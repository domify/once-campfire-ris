# Messages page benchmark

The Rust port's busiest page, `GET /rooms/:id/messages?before=`: 40
messages, 364,500 bytes of HTML, a signed session cookie, the same SQLite
database. ris, Rust and Go all answer it byte for byte as the Rust port
does; each keeps a per-message fragment cache, as the Rust port does.

- `messages_page.ri`: the ris server. Modes: `heap`, `tape`, `heap-cache`,
  `tape-cache` (on web), `tape-send` (web, the page sent from the
  tape with `Response#send`), `raw` (its own HTTP/1.1 loop, the response
  built on the request's tape and written from there), `threads N` (raw
  on N kernel threads in one process) and `tape-threads N` (tape-send on
  N kernel threads, a web server each, the port shared with
  `reuse_port`).
- `page.ri`: the renderer, generated by `gen_markup.py` from the Rust
  port's page (`page_head.ri.in` plus one message's markup).
- `go/`: the same page in Go (`net/http`, `mattn/go-sqlite3`).
- `loadgen/`: a keep-alive load generator in Go.

```sh
ris build bench/messages_page.ri -o bench/messages_page --release
bench/messages_page threads DB SECRET_KEY_BASE 8091 8
loadgen/loadgen URL COOKIE 64 10
```

## The app, 2026-10-17

`config/main.ri`: the same page through the whole app, as a request
reaches Rails' `MessagesController#index`. The kit's middleware, the
routes drawn as resources, `require_authentication` (the session looked
up on every request), `set_room`, the page query, the messages'
fragments from the fragment cache, `fresh_when` and every response header.
The bytes are the same as `bench/messages_page.ri`'s and the Rust port's,
and so are the last page, `after=` and the 204.

```sh
ris build config/main.ri -o campfire --release
./campfire DB SECRET_KEY_BASE 8091 [THREADS]
```

Same machine, idle, loadgen on cores 8-15; the server on core 0 or, with
8 threads, cores 0-7. Three 10 s runs with 64 connections; median and
fastest from one connection. `bench` is `tape-send` and `tape-threads 8`,
measured right after.

| | app (1 core) | bench (1 core) | app (8 threads) | bench (8 threads) |
|---|---|---|---|---|
| Requests/s | 3,943-3,958 | 8,500-8,683 | 8,624-9,061 | 25,174-26,834 |
| Median | 0.276 ms | 0.168 ms | 0.355 ms | 0.180 ms |
| Fastest | 0.235 ms | 0.148 ms | 0.252 ms | 0.150 ms |
| Slowest (p99) | 20-22 ms | 9 ms | 29-30 ms | 9-12 ms |
| Memory | 45 MB | 19 MB | 159 MB | 49 MB |

How it got here, one core:

- 250 requests/s: the kit's `Rack::ETag` digested the 364 KB body with
  std/digest's SHA-256, 2.9 ms a request. The ETag is now a SHA-256 over
  the parts, each fragment by a digest it works out once, as the Rust
  port's kit takes it (`RecordedPage#etag`).
- 1,800: the page was copied into one string twice, 729 KB of the 812 KB
  a request put on the heap. The kit's response now carries it in parts,
  the fragments shared with the cache, and the server joins them on the
  request's tape and sends them from there (`Parts`, `send_parts`): 77 KB
  a request.
- 2,550: every request still faulted in each page of the tape it wrote
  the page on, 85 faults. The kit runs the action in a task, so the
  request's scope stays open while it waits and the next connection opens
  another; the runtime kept one spare mapping a thread, and the rest
  came fresh from the kernel. ris now keeps up to 64, warm.
- 3,950: what is left is work the bench doesn't do. In the action
  (about 110 µs): the session, user, membership and room lookups, the
  page query, the ETag (its SHA-256 is still std/digest's) and the
  collector clearing the 77 KB.

Eight threads give the app 2.2 times its one core, the bench 3. What
grows past the cores' own slowdown is the runtime the threads share
(perf, CPU per request, one core to eight threads): the collector's mark
and sweep 30 to 178 µs, the allocator 21 to 91 µs, the runtime lock 2 to
74 µs, and putting each action's task on the one fiber list under that
lock 0 to 47 µs.

A process per core shares none of it: `./campfire DB SECRET 8091 shared`
eight times, the same cores 0-7, the same database:

## The app against the Rust port, 2026-10-17

Measured one after the other on the idle machine, the Rust port's release
binary on the same database, cores, loadgen and cookie. "8 CPUs" are
cores 0-7, four cores of two threads each; CPU and instructions are per
request, from `perf stat` over the servers.

| | Rust, 1 core | ris app, 1 core | Rust, 8 CPUs | ris app, 8 processes | ris app, 8 threads |
|---|---|---|---|---|---|
| Requests/s | 6,885 | 6,826-6,974 | 20,585 | 21,249-22,300 | 14,142-15,108 |
| Median (1 connection) | - | 0.200 ms | - | 0.214 ms | 0.225 ms |
| Slowest (p99) | 17 ms | 12-14 ms | 7 ms | 8-10 ms | 15-22 ms |
| CPU | 145 µs | 151 µs | 334 µs | 382 µs | 553 µs |
| User instructions | 271 K | 471 K | 272 K | 446 K | 623 K |
| Memory | | 20 MB | | 20 MB each | 68 MB |

Where the app was at the start of the day, 1,507 K user instructions a
request, and what took them out:

- The action's own task (`run_action`): every request's scope stayed open
  while it ran, so 64 connections wrote their pages on 64 tapes, 23 MB,
  out of cache, and put a fiber on the runtime's one list under its lock.
  The action now runs in the connection's task, web's isolation of which
  answers a panic with `public/500.html`.
- std/digest's SHA-256 padded a copy of its input a byte at a time and made
  an array for every block: 2.9 ms for the page, 280 K instructions for the
  ETag's 3.7 KB. It reads the blocks in place now: 1.1 ms, 11 µs.
- The ETag built its parts from substrings in a growing buffer, and the
  fragment cache keyed on a string a message: 29 KB and 7 KB a request,
  now 7 KB and nothing. The action puts 49 KB on the heap, from 77 KB.
- The response cache the Rust port has (`rils/kit/response_cache.ri`): the
  whole page, kept per user, session and request and dropped when any
  connection commits (`PRAGMA data_version`), so a repeat skips the page
  query, the fragments and the ETag.
- SQLite 3.53.2 linked in, multi-thread mode, as rusqlite builds and opens
  it: a few per cent on one core, nothing measurable on eight.

What is left is the threads: one process with eight of them shares a
collector and a runtime lock, and gives two-thirds of eight processes.

## The database

The page's database is the Rust port's own, made empty and filled by
hand. Start the Rust port's release binary on an empty directory
(`HTTP_PORT=8081 DISABLE_SSL=true RAILS_ENV=production
SECRET_KEY_BASE=$S CAMPFIRE_STORAGE_PATH=DIR
CAMPFIRE_DATABASE_PATH=DIR/db.sqlite3`, `S` 128 `a`s), sign up David
with `POST /first_run` (`user[name]`, `user[email_address]`,
`user[password]`, headers `Sec-Fetch-Site: same-origin` and `Origin`),
keeping the cookie jar, then insert 131 messages into room 1:

```python
t0 = datetime.datetime(2026, 10, 1, 9, 0, 0)
words = ("the quick brown fox jumps over lazy dog while campfire keeps "
         "<everyone> & their \"quotes\" warm").split()
for i in range(131):
    ts = (t0 + datetime.timedelta(minutes=i)).strftime("%Y-%m-%d %H:%M:%S.%f")
    cur = c.execute("insert into messages(client_message_id,created_at,"
                    "creator_id,room_id,updated_at) values(?,?,1,1,?)",
                    (f"bench-{i:03d}", ts, ts))
    text = " ".join(words[(i + k) % len(words)] for k in range(12 + i % 20))
    body = "<div>" + text.replace("&", "&amp;").replace("<e", "&lt;e") \
        .replace(">", "&gt;", 1) + "</div>"
    c.execute("insert into action_text_rich_texts(body,created_at,name,"
              "record_id,record_type,updated_at) "
              "values(?,?,'body',?,'Message',?)",
              (body, ts, cur.lastrowid, ts))
```

and `update action_text_rich_texts set body=replace(body,'&lt;everyone>',
'&lt;everyone&gt;')`, as Rails would have stored them: the bench and Go
print bodies as stored, the app and the Rust port sanitize them. Stop the
server and copy the database with `sqlite3 db.sqlite3 ".backup COPY"`
(the rows are in its WAL until then). `GET /rooms/1/messages?before=61`
is then 364,500 bytes from every server.

The app's memory grew with it: 55 MB on one core (20 MB), 60 MB a
process (20 MB), 159 MB with 8 threads (82 MB).

These are peak RSS figures, including shared library pages. Adding RSS
across processes counts those pages again for each process; the sum is
not their combined physical footprint. Use PSS and private memory from
`/proc/PID/smaps_rollup` alongside RSS when comparing processes and
threads. Reusable tape pages also contribute to RSS: keeping them warm
can avoid page faults on later requests, so judge that memory together
with throughput and latency rather than treating it as a leak.

## What it is not

- `raw` is not a whole HTTP server: no pipelining, timeouts or request
  bodies. The web package does those, and with `Response#send` it serves the page
  from the tape at 9,182 requests/s on one core (raw: 11,008).
- The fragment cache keys on the message's id and `updated_at`; the Rust
  port's key also names the creator and the room.
- The session cache never drops an entry; a real app drops it on sign-out.
